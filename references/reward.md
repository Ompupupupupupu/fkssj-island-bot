# 城战在线奖励领取（claim_online_reward.py / claim_seq.py 唯一权威）

> **职责**：城战在线奖励的手动单次领取、定时序列领取与不对称互斥规则。
> **何时读取**：用户说"领取城战在线奖励/帮我领取第x次奖励"、处理领取序列冲突、
> 关闭自动领取时。

## 脚本行为

- `scripts/claim_online_reward.py`：手动单次领取城战在线奖励：主界面 →"城战/世界"
  →"在线奖励"，点第 x 次领取按钮后回主界面（点击完成即视为领取成功，奖励到账
  以游戏内实际为准）。
  - 参数：领取次数 1-7
  - exit code：0=第 x 次领取成功且回主界面；1=参数错误/不在主界面/进界面失败/回主界面失败
- `scripts/claim_seq.py`：城战在线奖励 7 次序列领取（**必须后台启动**，供 20:25
  定时任务唤醒）：领第 1 次后，第 2-7 次分别在上次领取完成后间隔 1/2/3/4/5/5 分钟；
  某次失败也继续下一档；写 PID 文件（`$TEMP/fkssj_claim_seq.pid`），`--stop`
  按 PID 停止；启动时自动创建结果标记 `$TEMP/fkssj_claim_seq_done.pending`
  （结束后脚本自推结果并删除；日间直推失败保留作兜底信号）。
  - 参数：可选 `--stop`
  - exit code：0=7 次全部成功 / 停止正常（含未在运行）；1=不在主界面无法恢复 / 有领取失败 / 停止失败

**间隔从上次领取完成点起算**的设计原因：免疫 cron 触发漂移（保证奖励冷却时间
必被满足），也防 agent 前台等待超时；整个序列后台约 22 分钟完成并回主界面。

## 手动单次领取

用户说"帮我领取第 x 次奖励"时，先确认无后台长跑在跑（在跑先按用户意图停止或告知）
→ 前台运行（单次数秒即完，不会超时）：

```text
<PYTHON> <SKILL_DIR>/scripts/claim_online_reward.py <x>
```

## 自动序列领取（定时任务 20:25 唤醒后）

check_main 确认主界面 → 后台启动 `claim_seq.py`（同闯关的 PowerShell 分离启动器
形式，见 `references/battle.md`；日志重定向 `$TEMP/fkssj_claim_seq.log`）→ 等待约 5 秒确认
`$TEMP/fkssj_claim_seq.pid` 存在：存在则立即汇报"城战在线奖励领取已启动
（约 22 分钟），结束后会自动推送领取结果"；不存在则取日志与 err.log 尾部按
输出规范汇报启动失败。序列自行完成 7 次领取并回主界面。

`claim_seq.py` 启动时自动创建结果标记 `$TEMP/fkssj_claim_seq_done.pending`；
序列结束（含提前失败退出）**自动推送结果**（结束即推）：夜间只写夜间日志
`$TEMP/fkssj_night_events.log`（行格式 `[MM-DD HH:MM] 城战奖励: 摘要`）、日间经
`game_lib.push_weixin()` 直推微信（内置 30 秒推送锁，失败自动短时重试默认 3 次，
每次尝试记录到 `$TEMP/fkssj_push.log`），成功或已记录后删除标记；
**日间 3 次尝试全败则保留标记**，由检查类任务/夜间总结推送任务顺路兜底补推后删除
（见 `references/cron.md`；机制同闯关，详见 `references/battle.md`）。
`--stop` 强杀不进 finally 无自推，由停止方推送结果后删标记。

启动前若 `$TEMP/fkssj_claim_seq.pid` 已存在 → 不重复启动，直接汇报"序列已在进行"。

领取窗口守卫：奖励仅每天 20:00-21:00 可领，当前时间晚于 20:35 则不启动序列
（太晚启动会领不完全部 7 次），直接汇报"已错过今日领取窗口(20:00-21:00)"并结束。

## 不对称互斥规则（claim_seq 与其余脚本冲突时，唯一定义）

`claim_seq.py` 是短序列（约 22 分钟）后台长跑，与其余脚本互斥。与闯关的"让位"
不同——**它是定时唤醒的一次性序列，不会被其他任务优先停止**：

1. **检查类定时任务**（自动检查贸易/资源）执行时发现 `$TEMP/fkssj_claim_seq.pid`
   存在 → **跳过本轮**：不等待、不停止、不执行任何检查，直接结束本轮
   （下一轮 30 分钟后自然补上）。cron 会话不能前台干等约 22 分钟，也不应打断序列。
2. **用户当面任务**遇到序列在跑 → 询问用户："领取序列进行中（约 N 分钟后结束），
   等它结束还是现在停止？"经同意才 `claim_seq.py --stop`。
3. **错峰设计**：领取任务 cron 表达式为 `25 20 * * *`（20:25 触发，奖励仅每天
   20:00-21:00 可领），保证 20:00 贸易、20:05 资源检查先执行完、序列最后启动
   （同刻多任务优先级表见 `references/cron.md`）；20:30/20:35 检查轮若撞上仍在
   跑的序列，按规则 1 跳过，21:00/21:05 轮恢复正常。

每日晚间时间线：

```text
20:00  贸易检查触发（1-3 分钟结束）
20:05  资源检查触发（采集最坏 ~20:23 结束）
20:25  领取任务触发：让位 battle_run（如在跑）→ 防重复检查 → check_main → 后台启动序列
20:30  贸易检查轮遇 fkssj_claim_seq.pid 存在 → 跳过本轮
20:35  资源检查轮遇 fkssj_claim_seq.pid 存在 → 跳过本轮
~20:47 序列完成，自动回主界面（领取窗口 20:00-21:00 内留有余量）
21:00/21:05  贸易/资源检查轮恢复正常
```

## 关闭自动领取

关闭自动领取城战在线奖励定时任务时，若序列仍在后台运行，先运行
`claim_seq.py --stop` 再删任务（任务管理流程见 `references/cron.md`）。
关闭前若 `$TEMP/fkssj_claim_seq_done.pending` 存在且序列已结束（PID 不存在或进程
已死），取 `fkssj_claim_seq.log` 尾部把领取结果补推给用户并删除该标记（该标记是
日间直推失败的兜底信号），再删任务；序列仍在跑时按上文互斥规则询问用户后再停。
